# Operation Reference

Load only the operation that owns the request.

## `init`

Inspect the project first. Materialize `PRODUCT.md`, `DESIGN.md`, `surfaces/README.md`, and `DECISION-LOG.md` without overwriting existing files. Replace only project name and slug tokens. Leave unknown facts as explicit owner-input markers.

## `shape`

Produce scope, mode, audience job, current evidence, L0–L4 requirements, implementation boundaries, candidate directions when needed, acceptance criteria, and destructive-scope notes. Do not write production code.

## `build`

Require established truth and a selected direction. Follow the real stack. Create the smallest coherent surface that satisfies all requirements. Do not manufacture proof to fill layout slots.

## `refine`

Preserve identity, routes, behavior, content intent, and component ownership. Modify the smallest responsible files. If a requested change implies replacement rather than refinement, name the mismatch before proceeding.

## `redesign`

Preserve product truth, information requirements, and required behavior. Treat the incumbent visual world as evidence and anti-reference. Record the new direction in `DESIGN.md`. Deletions require explicit authorization.

## `study`

Extract macrostructure, hierarchy, type roles, color anchors, imagery logic, and interaction patterns. Do not clone pixels or proprietary assets. Record what is transferable and what is source-specific.

## `critique`

Evaluate without editing. Separate observed evidence, inferred mechanism, severity, and recommendation. Diagnose L0–L4 in order and identify blocked downstream judgments.

## `audit`

Use `references/audit-schema.md`. Run truth, content-preservation, perception, accessibility, responsive, state, anti-slop, performance, consistency, and verification-budget gates.

## `polish`

Run only after functional gates pass. Inspect once, correct the batched defect set, confirm once, and stop. Do not turn polish into a redesign.

## `harden`

Cover long text, localization, zoom, narrow viewports, empty/loading/error/success states, interrupted interactions, offline or unavailable dependencies, and recovery paths.

## `query`

Search one dominant concern using 2–10 meaningful terms. Specify domain, mode, or stack when known. Retry once with a narrower query if the first result is irrelevant. Do not persist an unverified match.

## `doctor`

Report stale context, missing required files, adapter hash drift, lock-schema failure, or conflicting project metadata. Do not repair unrelated drift as a side effect.

## `sync-upstreams`

Read `UPSTREAMS.lock.json`, fetch current default-branch heads, classify changes as compatible, conflicting, redundant, or irrelevant, and write a source-evaluation note before changing canonical behavior. Never update pins silently.
