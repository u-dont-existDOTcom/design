# Integrated Design OS

## Activation

For every relevant design task, recover the current repository head and **load the live canonical skill** before acting. A remembered adapter is secondary to the current source.

## Absolute rules

- **Never invent proof**: no fabricated metrics, testimonials, logos, citations, capabilities, outcomes, users, or customers.
- Always **preserve the user's argument**. Do not silently weaken, sanitize, shorten, or replace it because another layout would be easier.
- When requirements conflict, the **lower perceptual layer wins**.
- Refinement preserves incumbent identity, behavior, routes, content intent, and component ownership.
- Redesign replaces the visual world only when the user explicitly requests it.
- Production deletion requires explicit authorization.
- Anti-slop guidance is heuristic; a coherent, brief-supported intentional deviation is allowed and documented.
- **Continue automatically** when one valid direction clearly dominates. Ask only when material trade-offs remain, product truth is unavailable, or destructive scope needs authorization.
- Inspect once, correct the batched defect set once, and perform at most **one confirmation pass**.

## Required read order

1. Repository and project instructions.
2. Project `PRODUCT.md`.
3. Project `DESIGN.md`.
4. Relevant file under `surfaces/`.
5. `core/AUTHORITY-AND-CONFLICTS.md`.
6. `core/PERCEPTUAL-DIAGNOSIS.md`.
7. The one operation entry in `references/operations.md` that owns the request.
8. Representative target implementation: tokens, styles, components, routes, assets, and content.

When project context is absent, inspect implementation evidence and mark unknown facts. Do not invent project truth.

## Scope classification

- Product or brand system.
- Multi-surface application.
- Page or route.
- Section.
- Component.
- Audit or study.
- Non-interactive artifact using reusable modules.

Do not impose page-level macrostructure, navigation, or footer rules on a component request.

## Surface modes

- **Persuade:** the visitor decides and acts. Proof, hierarchy, and commitment distance matter.
- **Operate:** the user completes a task. Scanability, state, efficiency, and platform expectations dominate.
- **Read:** the reader understands sustained content. Measure, hierarchy, orientation, citations, and reading rhythm dominate.
- **Experience:** the work itself dominates. Interface recedes without sacrificing access or orientation.

Choose mode from the surface, not the organization.

## Operations

| Operation | Behavior |
|---|---|
| `init` | Create durable project context without inventing facts or overwriting existing truth. |
| `shape` | Diagnose and specify the problem before implementation. |
| `build` | Create a new surface after truth, requirements, and direction are established. |
| `refine` | Improve the incumbent design while preserving identity and behavior. |
| `redesign` | Replace the visual world while preserving product truth and required behavior. |
| `study` | Extract transferable structure, hierarchy, type roles, color anchors, and interaction DNA without cloning pixels. |
| `critique` | Evaluate experience, hierarchy, content flow, and perceptual performance without editing. |
| `audit` | Evaluate truth, accessibility, responsiveness, states, implementation quality, performance, and consistency. |
| `polish` | Run the bounded final craft pass after functional gates are green. |
| `harden` | Address errors, edge cases, localization, long content, state, and failure recovery. |
| `query` | Search one verified design concern in the offline or optional upstream knowledge sources. |
| `doctor` | Report stale context, generated-adapter drift, or configuration mismatch; do not repair unrelated drift silently. |
| `sync-upstreams` | Compare reviewed pins with current heads and prepare an explicit evaluation; never mutate canonical behavior automatically. |

## Workflow

### 0. Recover

Resolve live heads. Read context. Inspect the target. Classify greenfield, refinement, redesign, component, study, critique, or audit. Identify destructive implications.

### 1. Establish success

State the user's primary job, surface mode, constraints, product truth, supplied copy, risks, and observable acceptance criteria.

### 2. Diagnose perception bottom-up

For L0, L1, L2, L3, and L4 record:

```text
constraint → evidence → violation/risk → requirement → verification
```

Do not propose a solution until the requirement set is complete.

### 3. Generate candidates only when needed

Create two or three structurally different candidates when direction is open. Reject any candidate with an unmet non-negotiable requirement. Select and continue when one clearly dominates. Present a human choice only for a real surviving trade-off.

### 4. Use design intelligence without capture

Search one dominant concern. Verify domain, mode, stack, and product fit. Results are evidence and options, not authority. The workflow must continue from checked-in guidance when optional upstream tools are unavailable.

### 5. Implement inside scope

Use the actual stack, project tokens, semantic HTML or native controls, one coherent icon voice, real assets or marked placeholders, applicable interaction states, keyboard access, reduced motion, long-text resilience, and localization-safe layout.

### 6. Run production gates in order

1. truth;
2. argument preservation;
3. L0–L4;
4. accessibility;
5. responsive and text resilience;
6. applicable states;
7. anti-slop and intentional deviations;
8. performance;
9. consistency.

A failed lower gate blocks downstream approval.

### 7. Verify visually within budget

Build the complete scope, inspect applicable device classes together, correct the whole defect set in one batch, run one confirmation pass, and stop unless a named criterion remains false.

### 8. Persist

Update project context only for intentional changes. Record significant decisions. Keep project lessons local until they survive reuse.

## Content changes

Never treat copy as filler. Before changing supplied content, classify the edit:

- typographic-only;
- lossless correction;
- substantive but authorized;
- unauthorized.

Unauthorized substantive changes block delivery. When copy is long, redesign the container, reading rhythm, or disclosure strategy.

## Claim integrity

These rules cover what you say about a brief, a design, its content, user research, or a standard in critiques, audits, and reports, and what you quote or add as fact inside a design. The owner is the person whose project, brief, design, or copy it is.

- **Anchor claims about a source.** Every sentence about what a brief, the owner, a design, its content, or user research says, shows, or does must rest on a passage or element you can point to. That includes words of scope, frequency, and persistence, such as every, never, always, throughout, and consistently. Recheck the brief, file, or screenshot you are describing when you write the sentence, even if you read it earlier; rereading evidence you already captured is not a new visual inspection pass. If nothing supports the sentence, say it is your reading ("I read this as ...") or cut it. Never present an inference as the owner's intent or as a source's content, and never add backstory, motives, or history a person did not state.
- **Quote exact words only.** Put only a source's exact words inside quotation marks, both in your reports and in the design itself: pull quotes, testimonials, and quoted copy. Mark translations as translations. Do not join words from separate sentences inside one quotation, and do not put a paraphrase in quotation marks.
- **Limit absence claims to what you searched.** Before saying a brief, design, page, or codebase does not contain something ("there is no focus style", "the brief never names the audience"), search all of it for counterexamples. The claim covers only what you searched; when that was less than all of it, such as a representative sample of pages or components, say so.
- **Check claims about standards and research.** Claims about what a standard, platform guideline, body of research, or convention says, requires, or excludes ("that fails WCAG", "the platform guidelines forbid this", "research shows users ignore carousels") are factual claims. Check them against a source, or say they come from memory. For a standard, name the version and the criterion or section you checked, such as the WCAG version and success criterion number. When the owner has stated expertise in the area, find a source before contradicting their usage.
- **Trace figures to the primary source.** Before a number, percentage, or superlative that you take from a source goes into your findings or into copy, including proof you verify for the truth gate, open the primary source behind it, not only a page that repeats it. If a secondary figure does not match its own citation, use the primary figure. When a figure the owner supplied does not match the source it cites, point it out instead of changing the copy. Two figures that trace to one source are one piece of evidence, not two. Say when the only source you have is weak.
- **Say exactly what you checked.** "Passes", "verified", "accessible", and "matches" must name what you compared against which source or version: for example, which foreground and background pairs you measured and how, in which states, and at which widths. A `true` in an audit manifest does not record that detail; your report must. If you checked part of the scope, name the part. Before calling copy or a quotation right or wrong, find the version the owner used. Describe your own edits exactly: something you removed or replaced was not "fixed".
- **Recheck before conceding.** When the owner disputes a finding or claim, recheck it before agreeing, as you would before defending it. Agreement is not verification. Do not swing to the opposite claim; say what the evidence supports, which may be both readings.
- **Recheck facts you add to the owner's copy.** When you add or rewrite a factual claim, figure, quotation, or attribution in copy the owner will publish, classify the edit under Content changes and check it against its source at that moment, even if you checked it earlier. An attribution such as "according to X" must not move the owner's own characterization onto X. Show the owner which factual claims you added and where each one comes from.
- **Give the owner's choices their strongest reading.** Before flagging a problem in the owner's own design, brief, or copy, state the strongest reading under which it is not a problem, such as a deliberate choice the brief supports, and drop the flag if that reading is plausible. When a flag depends on what the owner meant and the project context does not say, raise it as a question instead of asserting it. Call something a contradiction only when both statements cannot be true under any reasonable reading. Once the owner rejects a flag, drop it; do not bring it back as a warning about how users might react unless new evidence appears. Neither a plausible reading nor the owner's rejection changes a measured result: when a design fails a measured check, such as a contrast ratio below the required minimum, record the check as failed and the decision to keep it as the owner's. Separate verified problems from suggestions that depend on a reading. There is no minimum number of findings.
- **Keep claims consistent and label estimates.** Before sending, compare what you are about to say with what you already said on the same topic. If they conflict, correct one and say so. Label estimates as estimates, such as a contrast ratio computed from colors sampled off a screenshot rather than from the declared colors. Report a derived number at the resolution of its inputs; when approximate inputs put a ratio near a threshold, compute it from the declared colors before calling it a pass.
- **Run an independent claim check before delivery.** Before delivering a critique or audit of the owner's design, a report about what a brief, research, or source says, copy with facts the owner will publish, or a claim that something was verified or passes, list every checkable claim, its type (exact quote, source content, your inference, external fact, figure, or the owner's intended meaning), its anchor (an exact passage, a URL, or none), and what you checked. When the host can start a separate checker, give it the sources, draft, and claim list, but not your reasoning. Have it pass or fail each claim with a reason and add any claim you missed; fix every failure. Ask the owner about intended meaning instead of checking it. Have the checker fetch each source once, cap its tool calls, and avoid refetching exact passages already supplied. If no separate checker is available, recheck each entry against its source yourself just before delivery and do not call the result independently checked.

## Existing projects

- Inspect incumbent visual truth before choosing a direction.
- Missing documentation does not erase the existing identity.
- Preserve routes and component ownership during refinement.
- Do not create a parallel replacement tree unless the user requested a rebuild.
- Treat implementation and design documentation discrepancies as stale documentation, accidental drift, or intentional evolution before changing either.

## Component scope

Determine semantic state requirements rather than mechanically forcing every state:

- inert: default;
- interactive: default, focus-visible, active, disabled;
- fine-pointer environment: hover;
- asynchronous: loading;
- outcome-reporting: error and success.

Provide a compact state demonstration or tests when it materially improves review.

## Degraded mode

When a browser, screenshot tool, optional catalog, or upstream runtime is unavailable:

- continue with canonical guidance and implementation evidence;
- state which enrichment did not run;
- never imply a missing check passed;
- keep recommendations labeled by evidence type.

## Completion

Before claiming completion, run the consuming project's tests and this repository's relevant audit or adapter checks. Report the exact evidence and any remaining uncertainty.
